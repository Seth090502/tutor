## 2. API shape

All of this is from `C:\LocalModel\CINFERENCE-v1.5-K7-INTEGRATION.md` section 4 (written 2026-09-29 from the shipped source; the file says its launcher commands were not executed) unless stated, cross-checked against `~/cinference-opt/campaign-v2/wt/goal-cum4/docs/serving.md`.

- **Endpoints [D].** `GET /health` (200 `{"status":"ok"}` or 503), `GET /v1/models` (one entry, `max_model_len` 262144), `GET /v1/models/{id}`, `POST /v1/chat/completions`, `POST /v1/responses` (+ `/input_tokens`, GET/DELETE `/{id}`), `POST /v1/messages`, `POST /v1/messages/count_tokens`. There is no `/v1/completions`, no `/v1/embeddings`, no audio. CORS is off. Every connection is closed after one response, so open a new connection per request.
- **Live response [M].** `{"data":[{"created":1790820247,"id":"qwen3.8-27b-huihui-abliterated-cinference","max_model_len":262144,"object":"model","owned_by":"ninfer"}],"object":"list"}`.
- **Request (chat) [D].** Required `model` (exact id, else 404) and `messages` (roles system, developer, user, assistant, tool; content string or text parts; images rejected, vision is off). Optional `max_tokens`/`max_completion_tokens` (default 32,768), `temperature`, `top_p`, `top_k`, `min_p`, penalties, `seed`, `stop` (up to 4), `stream`, `stream_options.include_usage`, `tools`, `tool_choice`, `reasoning_effort`, `enable_thinking`, `preserve_thinking`, `chat_template_kwargs`, `prompt_cache_key`. Unknown top-level fields are ignored.
- **Rejected with HTTP 400 [D].** JSON `response_format` and all grammar or guided decoding, `logprobs`, `n` > 1, `store:true`, `tool_choice` `required` or named, tool `strict:true`, `parallel_tool_calls:false` with tools, legacy `functions`, tool names outside `[A-Za-z0-9_-]{1,64}`, `reasoning_effort` other than `xhigh`, `medium`, `low`, `none`.
- **Sampling defaults [D: serving.md:811-816].** Thinking mode 1.0 / 0.95 / 20 / 0 / 0 (temperature, top_p, top_k, min_p, presence penalty) with a fresh random seed per request.
- **Response (non-stream) [D].** `choices[0].message` has `content`, `reasoning_content` (when non-empty), `tool_calls`; `usage` with `prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens`; a llama.cpp-style `timings` object.
- **Streaming [D].** SSE `data: {chat.completion.chunk}` lines. Order: role chunk, `: keep-alive` comments (after 5 s idle, also while queued or prefilling), `delta.reasoning_content` pieces (only before content), `delta.content` pieces, at most one `delta.tool_calls` chunk, a finish chunk (`stop`, `length`, `tool_calls`), a usage chunk when requested, then `data: [DONE]`. An error after the stream starts arrives as one `data: {"error":...}` event with no `[DONE]`. A disconnected client is detected within about 20 s. The HTTP body may stay open about 5 s after `[DONE]` [D: `CINFERENCE-HANDOFF.md:137-138`].
- **Limits [D].** Concurrency 1; up to 16 more requests wait; the 18th outstanding request gets 429; a request waiting over 600 s gets 503; body limit 384 MiB; prompt over 262,144 tokens gets 400 `context_length_exceeded`. To keep the full 32,768 output, keep the prompt under 229,376 tokens (derived in the integration doc).
- **Usable by the Python in libraryd tooling.** The integration doc section 4.11 contains a stdlib-only Python client (`wait_ready`, `chat`, `parse_sse`, `chat_stream`); the author says only `parse_sse` was run offline [D: integration doc 4.11].
- **Count tokens.** `POST /v1/messages/count_tokens` uses the artifact's tokenizer, chat template and media expansion [D: serving.md:724]. It is the only exact token counter the engine exposes, and it counts against the single request slot [E].

## 3. Tool and function calling

- **Supported, OpenAI format on the wire [D].** Request: standard `tools:[{"type":"function","function":{name,description,parameters}}]`, `tool_choice` `auto` or `none`. Response: `message.tool_calls=[{"id":"call_<16 hex>","type":"function","function":{"name","arguments":"<JSON string>"}}]`, `finish_reason:"tool_calls"`, `content` null when no text [D: integration doc 4.6].
- **Format inside the model [D].** The embedded Qwen3.8 chat template renders tools as a system-prompt block `# Tools ... <tools>` and the model replies `<tool_call>\n<function=NAME>\n<parameter=ARG>\nVALUE\n</parameter>\n</function>\n</tool_call>` [D: `C:\Qwen Local Harness\research\cinference-api-reference\qwen3_8.engine.jinja:68,140-149`]. This is Qwen's XML tool format, not Hermes JSON. The server parses that markup into structured calls; it does not execute anything and does not enforce your JSON schema, apply defaults, or use constrained decoding [D: serving.md:163-172].
- **Parallel calls [D/E].** The template loops over several `tool_calls` in one assistant message (`qwen3_8.engine.jinja:140-145`), and the server returns all calls of a turn together in a single stream chunk with no incremental argument deltas [D: integration doc 4.6]. `parallel_tool_calls:false` is rejected [D]. Whether the model actually emits several calls per turn is not measured here [E].
- **Where tool results go [D].** Send `{"role":"tool","tool_call_id":...,"content":...}`. The template renders each as `<|im_start|>user\n<tool_response>\n...\n</tool_response>`, merged into one user turn when consecutive (`qwen3_8.engine.jinja:102,163-167`). Assistant history with calls must carry `arguments` as a string and, with `preserve_thinking` on, the earlier `reasoning_content` verbatim, or the prefix cache misses [D: integration doc 4.5-4.6, 5].
- **Known failure modes [D].** Malformed markup, an undeclared tool name, a duplicate parameter, or a literal unmatched `</parameter>` inside an argument falls back to plain `content` text; a call cut off by `max_tokens` returns raw markup in `content` with `finish_reason:"length"` [D: serving.md:174-177; `CINFERENCE-HANDOFF.md:141-143`]. The quality candidates list (tool-call escaping, template parity with the official one) was not re-verified for K7 [D: integration doc section 1].
- **MCP.** The engine has no MCP client and rejects hosted or remote MCP tools in Responses and Messages requests [D: serving.md:507, 518, 639, 692]. My grep of the source tree for the word MCP (case-sensitive) found it only in `docs/serving.md` (4 hits) [M]. The acronym "mtp" in the sources is multi-token prediction, unrelated.
- **MCP in the harnesses around it.**
  - Claude Code (the "lane3" profile): has a native MCP client. It reaches the engine through the Anthropic Messages path: `C:\LocalModel\.cinference-opt\lane3\lane3.settings.json` sets `ANTHROPIC_BASE_URL=http://127.0.0.1:8000`, maps all model aliases to the local model id, `CLAUDE_CODE_EFFORT_LEVEL=xhigh`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW=224000`, `API_TIMEOUT_MS=1800000` [M: keys read, the auth token value was not printed]. That `/v1/messages` path is "not covered by the release gates" for K7 [D: integration doc 4.10].
  - Qwen Local Workbench (fork of Qwen Code, in `C:\Qwen Local Harness`): "Native memory, skills, hooks, MCP/LSP, subagents ... are kept" [D: `C:\Qwen Local Harness\AGENTS.md:56`]; it fixed an MCP post-startup delta bug [D: `WORKBENCH_STATE.md:257`].
  - DeepSeek harness (`dsh`, qualification candidate under the Workbench): provider route patch for the engine is documented in the integration doc section 6; I did not find MCP statements in its top-level README (grep, no match) [M], so its MCP support is **unverified**.
  - OpenCode local profile: `C:\LocalModel\LocalHarness\opencode.json` has `"mcp": {}` (supported key, no servers configured) [M].
  - DeepTutor: `C:\Users\sethy\Projects\tutor\deeptutor\services\mcp\` contains `manager.py`, `config.py` (`mcp.json` registry), `oauth.py`, `user_config.py`; MCP tools are exposed as `mcp_<server>_<tool>` with non-identifier characters sanitised [M: `manager.py:101-102`]. ## 7. Networking

- **WSL mode.** NAT. `C:\Users\sethy\.wslconfig` contains only `[wsl2] telemetry=false, memory=35000MB, maxCrashDumpCount=5` and `[experimental] autoMemoryReclaim=disabled`, no `networkingMode` [M]. Corroboration: a `vEthernet (WSL (Hyper-V firewall))` adapter at 172.23.128.1 exists on Windows [M]; WSL version 2.7.14.0 [M]. Microsoft: "By default WSL uses a NAT based architecture" [D: https://learn.microsoft.com/en-us/windows/wsl/networking]. `/etc/wsl.conf` only sets systemd and default user [M].
- **Windows to a WSL service.** Works via localhost forwarding: Microsoft says a Linux app is reachable from Windows "using `localhost`" [D: same URL]. Observed: `wslrelay.exe` holds Windows `127.0.0.1:8000` [M].
- **WSL to a Windows localhost service.** Not reachable via `127.0.0.1` in NAT mode. Microsoft: you "need to use the IP address of your host machine", obtained in Linux with `ip route show | grep -i default | awk '{ print $3}'`, and since such connections are treated as LAN connections the Windows service must accept them (for example bind `0.0.0.0` rather than `127.0.0.1`) [D: same URL]. Here the host gateway is likely 172.23.128.1 [E, from the adapter address]. Windows Defender Firewall applies to the host side; all three profiles are enabled [M]. Mirrored mode (`networkingMode=mirrored`) lets Linux reach Windows servers at `127.0.0.1` [D: same URL], but switching it is a `.wslconfig` change, which is an owner decision [D: `C:\LocalModel\CLAUDE.md:186-187`]. The Hyper-V firewall for WSL has `DefaultInboundAction=Block` and `DefaultOutboundAction=Allow` with only ICMP and mDNS allow rules [M]; this governs traffic into the WSL VM (for example LAN to WSL), not WSL to the host.

## 10. Recommendation: MCP client versus native bridge

**Recommendation: use an MCP client in the tutor's harness, with libraryd exposing MCP (rmcp). Keep a native gRPC (tonic) path as a second front door for non-agent callers, not as the way the engine's model reaches libraryd. Put any glue code in the tutor or libraryd repositories, never in the engine.**

Evidence and reasoning:

1. **The engine cannot be the MCP client or the bridge.** It does not execute tools or speak MCP; it only emits OpenAI `tool_calls` (section 3) and rejects remote MCP tool types [D: serving.md:507,518,639,692]. Every tool round trip is performed by the harness, which calls libraryd and sends the result back as a `tool` message. So "MCP client versus bridge" is a question about the harness only.
2. **Every harness in play already has an MCP client or an MCP slot**: Claude Code (native), Qwen Local Workbench (MCP/LSP kept as a product invariant), OpenCode (`mcp` config key, currently empty), DeepTutor (`deeptutor/services/mcp` with `mcp.json`, tool names sanitised to `mcp_<server>_<tool>`) (section 3). One MCP server then serves the tutor harness and Claude Code with no per-harness adapter. `dsh` MCP support is unverified.
3. **The engine's tool-name rule is compatible.** `[A-Za-z0-9_-]{1,64}`; name libraryd tools with that alphabet (no dots, no colons) so harnesses that pass names through do not trigger HTTP 400 [D: integration doc 4.2, 6.6]. DeepTutor sanitises names itself.
4. **Where a native bridge would live, if needed:** in the tutor application (a small client of libraryd's gRPC API that turns the OpenAI `tool_calls` into gRPC calls) or as an optional adapter crate in the libraryd repo. It must use `tool_choice:"auto"`, no `strict`, no `parallel_tool_calls:false`, and never send concurrent requests [D]. Do **not** put it in `~/cinference-opt` or `~/fast-long-context-cinference`: the K7 release is frozen read-only and verified by `SHA256SUMS` at every start, so any edit there makes the launcher exit 5 [D: `Start-Cinference-v1.5-K7.cmd:38-41`, integration doc 9 item 3]. A translating proxy in front of port 8000 is discouraged: the integration doc says "No shim is built or recommended here" and it adds a hop in front of a concurrency-1 server [D: integration doc 6.7]; use one only for a harness with no MCP and no custom endpoint.
5. **Constraints that libraryd's tool design must respect (all from the engine contract):**
   - Arguments arrive as one JSON string per call, no schema enforcement: libraryd must validate and return a short, actionable error so the agent loop can continue [D: serving.md:168-172].
   - Avoid literal `</parameter>` in arguments; for regex or code search queries that might contain markup, give the tool a base64 or a separate "mode" field only if testing shows failures (unmeasured) [D: serving.md:174-177].
   - Tool results sit in a `<tool_response>` user turn: keep results compact and citation-addressed (`{doc_id}#L{start}-L{end}`) to protect the 262,144-token window and the 100 %-hit prefix cache [D/M].
   - Keep the tool list and its JSON schema text byte-stable across turns: the prefix cache is exact-match, and a changed tools block forces a re-prefill (cold 247K prefill about 74 s, 165 s in total for the capacity request) [D: integration doc 4.5, 4.9, 5 item 5]. The harness-side tool list currently has 10 tools [M: K7 log]; each extra schema costs prompt tokens.
   - One engine slot: the tutor, Claude Code, Workbench and OpenCode all queue behind each other, and a waiter over 600 s gets 503 [D]. Tool execution happens outside the engine, so libraryd latency does not hold the slot while the model is idle between turns, but a second client mid-conversation can evict the cached prefix (observed A/B/A eviction) [D: `CINFERENCE-HANDOFF.md:135-137`].
   - Return the tool-call turn to the model with `reasoning_content` replayed unchanged [D].
6. **Stage 2 [E].** The engine is tied to the RTX 5090 (sm_120a), so the tutor model stays on the main PC; the AI PC (RX 7800 XT, Vulkan llama.cpp) would host vault, sidecars and embedding. Then libraryd listens on the LAN with authentication (the harness on the main PC is the only client that matters), the engine stays loopback-only, and only the harness-to-libraryd link crosses the network. This keeps the engine's "no non-loopback bind" boundary intact. I have not tested any cross-machine path.
7. **Where libraryd runs in Stage 1 [E].** A Windows-native libraryd on `127.0.0.1` is reachable from the Windows harness and Claude Code directly, like the engine. If libraryd runs in WSL, Windows clients still reach it through localhost forwarding, but WSL-resident clients cannot reach Windows localhost services in NAT mode (section 7). That is the case for keeping all tutor-side processes on the same side as libraryd, or asking the owner about mirrored mode.
